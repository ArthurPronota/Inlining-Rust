# Inlining в Rust

## 🧩 Что такое инлайнинг

**Inlining** — это оптимизация компилятора, при которой **тело функции подставляется непосредственно в место её вызова** вместо генерации инструкции `call` (или эквивалентной).

**Было:**
```asm
call my_add          ; переход в функцию
; ... тело my_add ...
ret                  ; возврат
```

**Стало (после инлайнинга):**
```asm
add eax, ebx         ; тело my_add встроено прямо сюда
; никакого call/ret
```

### 🎯 Что даёт инлайнинг

| Плюс | Минус |
|------|-------|
| Нет накладных расходов на вызов (`call`/`ret`, сохранение регистров) | Код «раздувается» (code bloat) |
| LLVM видит больше контекста → лучше оптимизирует | Кэш инструкций CPU может не вместить |
| Константы из места вызова «просачиваются» в тело | Сложнее отлаживать (функция «растворяется») |
| Убираются неиспользуемые ветки (если аргументы константы) | Время компиляции растёт |

## 🧠 Как компилятор решает

Компилятор сам решает, что инлайнить, опираясь на:

- **размер функции** — маленькие инлайнятся охотнее,
- **число вызовов** — одна точка вызова → выше шанс,
- **profile guided optimisation (PGO)** — реальные данные профилирования,
- **эвристики LLVM** — стоимость вызова vs стоимость встраивания.

Обычно **маленькие функции инлайнятся автоматически**, без атрибутов. Атрибуты нужны, когда эвристика ошибается.

## 🏷️ Атрибуты

| Атрибут | Значение |
|---------|----------|
| `#[inline]` | **Подсказка**: «стоит встроить» |
| `#[inline(always)]` | **Требование**: «встрой обязательно» (если возможно) |
| `#[inline(never)]` | **Запрет**: «никогда не встраивай» |
| (без атрибута) | Решает LLVM по эвристике |

### 1️⃣ `#[inline]` — для библиотек

**Главная причина:** без `#[inline]` функция из **другого crate** не может быть заинлайнена.

Почему: Rust компилирует каждый crate **отдельно**. Тело функции из библиотеки **недоступно** в бинарнике-потребителе — только её сигнатура. LLVM не может встроить то, чего не видит.

`#[inline]` говорит: **«положи тело функции в метаданные crate'а»**. Тогда потребитель сможет её инлайнить.

```rust
// lib.rs (крейт mylib)
#[inline]
pub fn my_add(a: u32, b: u32) -> u32 {
    a.wrapping_add(b)
}
```

```rust
// main.rs (потребитель)
use mylib::my_add;

fn main() {
    let x = my_add(1, 2);   // ← может быть заинлайнено, потому что #[inline]
}
```

**Без `#[inline]`** — вызов через `call` останется, потому что LLVM не видит тело.

⚠️ **Не путать с generic'ами.** Generic-функции **всегда** инлайнятся в месте мономорфизации — `#[inline]` для них не нужен.

### 2️⃣ `#[inline(always)]` — редко, для тонких обёрток

**Когда ставить:**

- **Тонкие обёртки над интринзиками** — например, `a.wrapping_add(b)`, `_mm256_add_ps(a, b)`, `ptr.read()`.
- **Функции из 1–3 инструкций**, где вызов дороже тела.
- **Горячий путь**, где каждая наносекунда важна.

**Ваш пример:**

```rust
#[inline(always)]
fn my_add(a: u32, b: u32) -> u32 {
    a.wrapping_add(b)   // ← одна инструкция add
}
```

`my_add` — **тонкая обёртка** над `wrapping_add`. Без инлайнинга был бы `call` + `add` + `ret` вместо просто `add`. `#[inline(always)]` гарантирует, что вызов исчезнет.

**Когда НЕ ставить:**

- Большие функции — раздуют код.
- Функции, вызываемые из многих мест — code bloat.
- Если не уверены — **не ставьте**. LLVM часто и так инлайнит.

**Правило:** `#[inline(always)]` — **редкий** атрибут. Обычно для **тонких обёрток** над интринзиками и **критичных** горячих путей после профилирования.

### 3️⃣ `#[inline(never)]` — для холодного кода

**Когда ставить:**

- **Error reporting** — код обработки ошибок выполняется редко, но занимает место.
- **Panic-пути** — `unwrap_or_else`, `expect`.
- **Редкие ветки** — логирование, fallback.
- **Бенчмарки** — чтобы честно замерить функцию.
- **Отладка** — чтобы функция была видна в ассемблере.

**Зачем:** если холодный код **не** инлайнится, он остаётся **отдельной функцией**, и **горячий путь** не раздувается. Кэш инструкций CPU лучше используется.

```rust
#[inline(never)]
fn report_error(e: &Error) {
    // большой код форматирования, логирования, отправки
    // выполняется редко — не должен занимать место в горячем пути
}

fn hot_path(x: u32) -> u32 {
    if x == 0 {
        report_error(&Error::Zero);   // ← call, не inline
        return 0;
    }
    x * 2   // ← горячий путь, компактный
}
```

## 📊 Сводная таблица

| Атрибут | Когда | Пример |
|---------|-------|--------|
| **`#[inline]`** | Функции в **библиотеках** (cross-crate) | `pub fn` в lib.rs |
| **`#[inline(always)]`** | **Тонкие обёртки** над интринзиками | `wrapping_add`, `_mm256_add_ps` |
| **`#[inline(never)]`** | **Холодный код**: ошибки, panic, логирование | `report_error`, `expect` |
| **(без атрибута)** | Обычные функции — LLVM сам решит | 90% кода |

## 💻 Ваш пример

```rust
#[inline(always)]
fn my_add(a: u32, b: u32) -> u32 {
    a.wrapping_add(b)
}

fn main() {
    let a = 200u32;
    let b = 255u32;
    println!("my_add({}, {}) = {}", a, b, my_add(a, b));       // 455
    println!("my_add({}, {}) = {}", u32::MAX, b, my_add(u32::MAX, b)); // 254
}
```

### 📝 Что происходит

**`wrapping_add`** — сложение с **переполнением** (wrap around):

| Выражение | Обычное `+` | `wrapping_add` |
|-----------|-------------|----------------|
| `200 + 255` | `455` | `455` |
| `u32::MAX + 255` | **panic** (overflow) в debug | `254` (wrap) |

`u32::MAX = 4294967295`. `4294967295 + 255 = 4294967550`, но `u32` вмещает до `4294967295`. Переполнение:

```
4294967295 + 255 = 4294967550
4294967550 mod 2^32 = 4294967550 - 4294967296 = 254
```

**Почему `wrapping_add`, а не `+`:**

```rust
fn my_add(a: u32, b: u32) -> u32 {
    a + b   // ❌ panic в debug при переполнении
}
```

В **debug**-сборке `a + b` при переполнении **паникует** (`attempt to add with overflow`). В **release** — wrap'ается (но это UB-подобное поведение, зависит от настроек). `wrapping_add` — **явно** говорит: «переполнение допустимо, wrap».

**`#[inline(always)]`** — потому что `my_add` — **тонкая обёртка** над `wrapping_add` (одна инструкция `add`). Без инлайнинга был бы `call` + `add` + `ret`. С `#[inline(always)]` — просто `add`.

### 🔍 Проверка через ассемблер

```bash
cargo rustc --release -- --emit=asm
```

В `.s`-файле `my_add` **не будет отдельным символом** — её тело встроено в `main`:

```asm
; вместо:
; call my_add
; ...
; my_add:
;   add eax, ebx
;   ret

; будет:
add eax, ebx   ; тело my_add прямо в main
```

Если убрать `#[inline(always)]` — LLVM **всё равно** может инлайнить (функция крошечная). Но `#[inline(always)]` **гарантирует** это.

## ⚠️ Важные нюансы

**1. `#[inline(always)]` — не абсолютная гарантия.**

LLVM **обычно** уважает, но при `-C opt-level=z` (оптимизация по размеру) или LTO может проигнорировать. На практике — уважает.

**2. Не путать с `#[no_mangle]`.**

| Атрибут | Про что |
|---------|---------|
| `#[inline(always)]` | Про **встраивание** |
| `#[no_mangle]` | Про **имя символа** (для FFI) |
| `#[cold]` | Подсказка: «редко вызываемая» |

Часто используют вместе:

```rust
#[no_mangle]
#[inline(never)]
pub extern "C" fn my_func() { ... }
```

**3. Generic-функции инлайнятся всегда.**

```rust
fn generic_add<T: Add<Output = T>>(a: T, b: T) -> T {
    a + b   // мономорфизация → тело известно → инлайн
}
```

`#[inline]` для generic'ов **не нужен** — они компилируются в каждом crate-потребителе.

**4. Cross-crate инлайнинг требует `#[inline]`.**

Без `#[inline]` функция из библиотеки **не** будет встроена в бинарник-потребитель, потому что тело недоступно. `#[inline]` кладёт тело в **метаданные** crate'а.

**5. `#[inline(always)]` и code bloat.**

Если функция вызывается из **100 мест**, `#[inline(always)]` создаст **100 копий** тела. Для большой функции — катастрофа для кэша инструкций. Ставьте **только** для тонких обёрток.

**6. `#[inline(never)]` и бенчмарки.**

Без `#[inline(never)]` компилятор может встроить функцию в `main`, и вы измерите **не** функцию, а часть `main`. С атрибутом — честный `call`.

**7. `#[cold]` — альтернатива `#[inline(never)]`.**

```rust
#[cold]
fn report_error(e: &Error) { ... }
```

`#[cold]` говорит LLVM: «эта функция выполняется редко». LLVM сам решит **не** инлайнить её в горячий путь. Часто **лучше**, чем `#[inline(never)]`, потому что даёт больше информации.

## 🎯 Практические рекомендации

| Ситуация | Что делать |
|----------|-----------|
| Обычная функция | **Ничего** — LLVM сам решит |
| Функция в библиотеке (cross-crate) | `#[inline]` |
| Тонкая обёртка над интринзиком | `#[inline(always)]` |
| Error reporting, panic-путь | `#[inline(never)]` или `#[cold]` |
| Бенчмарк | `#[inline(never)]` |
| Generic-функция | **Ничего** — инлайнится автоматически |
| Не уверены | **Ничего** — не ставьте атрибут |

## 🎯 Итог

**Inlining** — оптимизация, при которой тело функции встраивается в место вызова. Компилятор решает сам, но **атрибуты** дают подсказки:

1. **`#[inline]`** — для **библиотек**, чтобы cross-crate вызовы могли инлайниться. Без него тело недоступно в потребителе.
2. **`#[inline(always)]`** — **редко**, для **тонких обёрток** над интринзиками (`wrapping_add`, `_mm256_add_ps`). Гарантирует встраивание.
3. **`#[inline(never)]`** — для **холодного кода** (ошибки, panic, логирование), чтобы не раздувать горячий путь. Альтернатива — `#[cold]`.

**Ваш пример:** `my_add` — тонкая обёртка над `wrapping_add`. `#[inline(always)]` гарантирует, что вызов исчезнет и останется одна инструкция `add`. `wrapping_add` нужен, потому что `u32::MAX + 255` переполняется — обычный `+` паниковал бы в debug.

**Главное правило:** **не ставьте атрибуты без причины**. LLVM инлайнит 90% кода сам. `#[inline]` — для библиотек, `#[inline(always)]` — для тонких обёрток, `#[inline(never)]` — для холодного кода. Всё остальное — преждевременная оптимизация.
